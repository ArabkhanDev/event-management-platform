# Deployment — free tier

| Piece | Host | Free tier |
|---|---|---|
| Frontend (Vite/React) | Vercel | Unlimited static hosting, global CDN |
| Backend (Spring Boot) | Render | 512 MB / 0.1 CPU, sleeps after 15 min idle |
| Database (Postgres) | Neon | 0.5 GB storage, permanent (no 30-day expiry) |
| Email relay | Brevo | 300 emails/day, SMTP on port 2525 |

No credit card is required for any of the four.

---

## 0. Before anything: revoke the leaked Gmail password

`backend/src/main/resources/application.yml` previously carried a real Gmail
address and app password as defaults, and that file is in the public GitHub
history. The defaults are now gone, but the credential is still valid until you
revoke it: <https://myaccount.google.com/apppasswords> → delete the entry.

Removing it from the current file does **not** remove it from git history. If
the repository is public, treat the password as compromised regardless.

## 1. Database — Neon

1. Sign up at <https://neon.com> and create a project.
   - Region: **AWS eu-central-1 (Frankfurt)** — same region as the Render service.
   - Database name: `meet2be`.
2. On the project dashboard open **Connection details** and switch the snippet
   type to **Java / JDBC**. Also turn **Connection pooling OFF** — Hibernate
   holds its own pool, and Neon's pgBouncer endpoint breaks prepared statements.
3. You get something shaped like:

   ```
   jdbc:postgresql://ep-cool-name-123456.eu-central-1.aws.neon.tech/meet2be?sslmode=require
   ```

   Keep the host string, the username, and the password — you need all three in
   step 2. `sslmode=require` is mandatory; Neon refuses plaintext connections.

Tables are created automatically on first boot (`ddl-auto: update`).

> **Watch the 0.5 GB ceiling.** Rendered presentation slides are stored in
> Postgres as `bytea`, roughly 300–600 KB per slide. That is ~1,000 slides
> before the free tier is full. See "Known limits" below.

---

## 2. Backend — Render

1. Sign up at <https://render.com> with your GitHub account and grant it access
   to `ArabkhanDev/event-management-platform`.
2. **New → Blueprint**, pick the repository. Render reads `render.yaml` from the
   repo root and proposes a service named `meet2be-api`.
3. It will prompt for every variable marked `sync: false`. Fill in:

   | Variable | Value |
   |---|---|
   | `DB_URL` | the full JDBC URL from step 1 |
   | `DB_USER` | Neon username |
   | `DB_PASSWORD` | Neon password |
   | `CORS_ORIGINS` | leave as `http://localhost:5173` for now — updated in step 4 |
   | `PUBLIC_APP_BASE_URL` | same placeholder for now |
   | `PUBLIC_API_BASE_URL` | `https://meet2be-api.onrender.com` |
   | `MAIL_USERNAME` | Brevo SMTP login (step 3) |
   | `MAIL_PASSWORD` | Brevo SMTP key (step 3) |
   | `MAIL_FROM` | the sender address you verified in Brevo |

   `JWT_SECRET` is generated by Render — do not set it yourself.

4. Deploy. The first build takes 5–10 minutes (Gradle downloads the world).
   When it finishes, `https://meet2be-api.onrender.com/actuator/health` should
   return `{"status":"UP"}`.

## 3. Email — Brevo

Render's free plan blocks outbound TCP to ports **25, 465 and 587**, which rules
out Gmail SMTP entirely. Brevo also listens on **2525**, which is not blocked,
so `spring-boot-starter-mail` keeps working with only a config change.

1. Sign up at <https://www.brevo.com>.
2. **Senders, Domains & Dedicated IPs → Senders** — add and verify the address
   you want mail to come from. Use that as `MAIL_FROM`.
3. **SMTP & API → SMTP** — copy the login and the SMTP key into `MAIL_USERNAME`
   and `MAIL_PASSWORD`.

`MAIL_HOST` (`smtp-relay.brevo.com`) and `MAIL_PORT` (`2525`) are already set in
`render.yaml`.

If mail still times out, Render is blocking 2525 too — in that case the relay
has to move to an HTTPS API, which is a code change to the mail service rather
than configuration.

## 4. Frontend — Vercel

1. Sign up at <https://vercel.com> with GitHub and import the same repository.
2. Set **Root Directory** to `frontend`. The rest (framework, build command,
   output directory) comes from `frontend/vercel.json`.
3. Add one environment variable, for all environments:

   ```
   VITE_API_BASE = https://meet2be-api.onrender.com/api
   ```

   Vite inlines `VITE_*` at build time, so this must exist *before* the build —
   changing it later requires a redeploy, not just a restart.
4. Deploy. Note the resulting domain, e.g. `https://meet2be.vercel.app`.
5. Go back to Render → `meet2be-api` → **Environment** and correct:

   ```
   CORS_ORIGINS        = https://meet2be.vercel.app
   PUBLIC_APP_BASE_URL = https://meet2be.vercel.app
   ```

   Saving triggers a redeploy. This step is not optional — both the REST CORS
   filter and the SockJS handshake read `CORS_ORIGINS`, so WebSockets fail
   silently until it matches the real origin.

   Vercel gives every branch and PR its own preview domain, and those are *not*
   covered by an exact-match origin. `CORS_ORIGINS` is matched with Spring's
   `allowedOriginPatterns`, so `https://*.vercel.app` works if you want previews
   to reach the API — at the cost of allowing any Vercel-hosted site to call it.

---

## 5. Verify

```bash
curl https://meet2be-api.onrender.com/actuator/health
```

Then open the Vercel URL, register an account, create an event, and open the
attendee view in a second tab to confirm the WebSocket pushes updates live.

The very first request after 15 minutes of silence takes **30–60 seconds** —
Render is cold-starting the container and the JVM. Subsequent requests are fast.

## Known limits of this setup

**Cold starts.** Free Render services sleep after 15 minutes of inactivity. For
a live event that is disruptive: the first attendee to scan the QR code waits a
minute. Options: keep a browser tab polling `/actuator/health` during the event,
or upgrade to Render's $7/month Starter plan (which also unblocks port 587).

**Slide rendering vs. 512 MB.** `PresentationServiceHandler.renderAndStoreSlides`
loads the entire PDF into a byte array and accumulates every rasterised page in
a `List` before saving. At 110 DPI a page is ~6 MB in heap, so a large deck can
exhaust the container. `MAX_UPLOAD_SIZE` is capped at 10 MB to compensate;
streaming each page straight to the database would remove the ceiling.

**`ddl-auto: update`.** Hibernate mutates the production schema on every boot.
It never drops columns, so it silently accumulates dead ones, and it cannot
express data migrations. Fine for a demo, not for anything with real users —
`backend/CLAUDE.md` forbids it for exactly this reason. Flyway is the fix.

**Neon storage.** 0.5 GB, mostly consumed by slide images. `SELECT
pg_size_pretty(pg_database_size('meet2be'))` to check.

**In-memory STOMP broker.** `enableSimpleBroker` keeps subscriptions in the
JVM's heap, so the service cannot be scaled past one instance without attendees
missing messages. Not a constraint on the free tier (one instance is all you
get), but it blocks horizontal scaling later.
